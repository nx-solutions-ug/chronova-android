# Wiki Pipeline

The wiki is generated by a separate tool (`@chronova/wiki-agent`,
installed via Bun) and published to the repository's GitHub Wiki tab. A
flattening step converts the nested `.wiki/` directory into the flat
layout the Wiki tab expects (e.g. `.wiki/architecture/overview.md` →
`Architecture-Overview.md`).

The pipeline runs on three triggers:

- `push` to `main` — keeps the wiki in sync with merged content.
- `schedule` — `0 8 * * *` (daily) — catches content drift.
- `workflow_dispatch` — manual reruns.

## Flow

1. **Checkout** — uses the GitHub App token when available, otherwise
   the default `GITHUB_TOKEN`.
2. **Setup Bun** (`oven-sh/setup-bun@v2`) and **Setup Node.js 25**
   (`actions/setup-node@v7`).
3. **Install** `bun add -g @chronova/wiki-agent`.
4. **Run** `wiki --update --print --verbose --wiki`. The agent
   inspects the repository and writes its output under `.wiki/`. The
   `--print` flag echoes the run report to stdout.
5. **Generate timestamp** — `date +%s` (Unix seconds). This is the
   staging branch suffix.
6. **Diff detection** — `git status --porcelain .wiki` collects the
   list of changed files. The run metadata files
   (`.wiki/.last-update-report.md`, `.wiki/.last-updated.json`) are
   excluded so a no-op content change does not open a PR.
7. **Wiki initialization check** — `git ls-remote` against the
   `<owner>/<repo>.wiki.git` repo. If the wiki repo has never been
   initialized the workflow posts a warning and the staging PR still
   opens, but the publish step is skipped.
8. **Publish** (when the wiki repo is initialized and there are content
   changes):
   - Run `wiki-flatten "$GITHUB_WORKSPACE/.wiki" /tmp/wiki-flat` to
     produce the flat layout.
   - Clone the wiki repo into `/tmp/wiki`.
   - `rsync -a --delete --exclude='.git' /tmp/wiki-flat/ ./` to mirror
     the flattened output. `--exclude='.git'` protects the wiki clone's
     git directory.
   - Commit as `wiki-agent[bot]` and push to `master`. If the push
     fails, the workflow emits an `::error::` annotation and exits
     non-zero so the failure is visible.
9. **Staging PR** — `peter-evans/create-pull-request@v8` opens a PR
   with branch `wiki/staging-<timestamp>` (e.g. `wiki/staging-1731417600`),
   title `docs: wiki staging snapshot`, body the report from
   `.wiki/.last-update-report.md`, and `--add-paths .wiki`.

The staging PR is the human review surface. Once merged, the next run
that detects content changes will re-publish to the wiki repo.

## Stale PR handling

The `wiki/staging-<timestamp>` branch includes the Unix epoch at the
moment the workflow ran. The wiki agent checks open staging PRs:

- A staging PR whose branch timestamp is **greater than or equal to**
  the latest commit timestamp already reflects current content. The
  agent abandons the update so it does not overwrite a newer pending
  review.
- A staging PR whose branch timestamp is **older than** the latest
  commit timestamp is stale. The agent comments
  *"This branch is from an earlier staging run and is stale. Closing"*
  and closes it before opening its own.

This keeps the PR queue clean and avoids racing newer content with
older snapshots.

## Model configuration

`WIKI_OLLAMA_MODE=cloud` selects the OMP cloud provider. The
`WIKI_OLLAMA_API_KEY` secret is required. The model is controlled by
the `WIKI_MODEL` variable (default `kimi-k2.7-code`).

## Required secrets

| Secret | Used for |
|--------|----------|
| `WIKI_PUSH_TOKEN` (preferred) | Pushing to the wiki repo. Falls back to the GitHub App token. |
| `WIKI_OLLAMA_API_KEY` | The LLM provider key. |
| `APP_CLIENT_ID` / `APP_PRIVATE_KEY` | The `chronova-agent` GitHub App credentials used by every workflow. |
| `OLLAMA_API_KEY` | Used by the OMP agent (separate from the wiki LLM). |

## Local preview

Run the same toolchain locally to preview the wiki without pushing:

```bash
bun add -g @chronova/wiki-agent
wiki --update --print --verbose
```

The flattened output is not produced locally — that step runs in CI
via `wiki-flatten`. Use the staging PR as the review surface.
